# Recording and concurrent capture evidence, 2026-09-08

The implementation separates encoder startup from recorded time, retains a timestamp-zero frame when stopping during startup, and owns reusable GDI resources on the recorder thread. Screenshot selection/editor windows require successful capture exclusion before showing; that requirement remains active until a stopping recorder thread exits. The async persistence-to-editor transition restores WPF dispatcher affinity even when invoked from a native STA hotkey callback.

The resource contract follows Microsoft's [GetDIBits documentation](https://learn.microsoft.com/en-us/windows/win32/api/wingdi/nf-wingdi-getdibits): deselect the bitmap before readback and require every requested row. Control exclusion uses [SetWindowDisplayAffinity](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setwindowdisplayaffinity) with `WDA_EXCLUDEFROMCAPTURE`. The explicit recording clock remains included.

## Reproduction and scope

Run the Release application with:

```powershell
MyCapture.exe --selftest-recording-performance <absolute-output-directory>
```

The diagnostic creates its own blue fixture; captured rectangles remain inside it. It alternates the original `CaptureRegionInto` path and reusable `CaptureSession` path, 64 samples each at 320×240 and 1280×720 after warming both. It then records each size for approximately six seconds after readiness, decodes the MP4, and records a separate selector/editor/clock scenario. Per-path raw frame times, median, p95, maximum, managed allocations and process CPU are written to JSON. CPU is normalized as process CPU milliseconds / wall milliseconds / 16 logical processors × 100. Process CPU has coarse resolution, so short per-call totals can be zero. Recording-interval CPU excludes encoder initialization and finalization; phase timing totals are wall time, not CPU attribution.

No raw user pixels, clipboard payloads or capture-library files are used. All native windows close when the diagnostic ends. These static-source results do not prove animation throughput, mixed-DPI behavior, or a steady 30/60 fps rate.

There is no demonstrated capture-latency or sustained-fps speedup. The measurable change is removal of repeated managed callback allocations and native DC/bitmap construction. Capture wall time dominates synchronous encoding; allocation improvement must not be presented as a 30 fps result.

The concurrent MP4 was decoded at settled timestamps in four phases. Plain, excluded selector and excluded editor each had zero changed pixels in the fixed clock/overlay probe area. The intentionally included clock had 5,130 changed decoded pixels. The selector used a synthetic magenta image, making failed exclusion visible. These are actual MP4 pixel observations, plus a successful exclusion return before window show; they do not replace interactive hotkey/drag/DPI QA.

## Coordinated quiet repeat and limits

`artifacts/validation/recording-performance-quiet/` also returned **PASS**, with lead UI/build work paused. OS and other application load were still uncontrolled. This repeat briefly tested preparing native resources before encoder initialization; that optional ordering change was not retained. Final production code preserves the accepted encoder-first/lazy-capture order. Do not use this repeat as exact-final-source startup evidence.

Original/reusable medians were 47.373/50.269 ms at 320 and 52.017/51.642 ms at 1280. The 1280 per-path process CPU totals were 265.625/187.500 ms, while the 320 totals both resolved to zero. Native handle delta remained zero. This run again does not establish a reliable latency improvement.

Current-recording measurements were 116 frames / 6,025.973 ms (19.250 fps) at 320 and 141 / 6,030.566 ms (23.381 fps) at 1280. Concurrent decoded probe counts were again zero for plain/selector/editor and 5,127 for the included clock. A premature inference that this run had hung was corrected after reading its completed PASS report: initialization was 771.001 ms at 320. No process was terminated and no report was changed.

Earlier `recording-performance-run1` failed its first MP4 seek with HRESULT `0xC00D36E5`; `run2` reported a 15-second readiness timeout. Those failures remain on disk. The accepted run canonicalizes output paths and creates/uses/disposes its decoder on one MTA thread. These changed together, so the precise cause of the earlier failures is not established.

## Verification and remaining work

- 35 focused lifecycle/scenario/recording/editor-transition tests passed on the accepted production ordering; 0 skipped. The stop-during-persistence regression initially exposed missing dispatcher context and passed after correction.
- A broader 72-test capture/recording/clock run passed during the temporary resource-preparation experiment; 0 skipped. The final experiment was removed, leaving accepted production behavior and diagnostic/documentation additions. Final Release compilation completed with 0 warnings/errors.
- Native tests require desktop access. Sandboxed tests failed with `BitBlt` access denied; the same scoped tests succeeded outside the sandbox. Dependency restore and vulnerability audit succeeded without disabling audit.
- Resource tests preserve the original-path expected pixels, compare reusable output against them, exercise buffer-validation failure/retry/dispose/restart, and check GDI object counts. Encoder lifecycle tests compare actual factory, write and disposal thread IDs.

Remaining broader acceptance includes actual user hotkey overlap and repeated capture/persistence/close scenarios, pin drag/idle measurements, OCR/index/persistence cost, DPI/hardware QA, and final integrated Release/package checks. The existing Media Foundation factory and finalization calls can block; asynchronous stop keeps the dispatcher available but does not provide a hard COM completion deadline. The sub-millisecond pacing remainder currently spins; its CPU impact needs measurement before changing cadence.
