The final run is `artifacts/validation/pin-storage-verified/pin-storage-performance.json`; its sibling report says `RESULT: PASS`, and the process exited 0. The lead closed its synthetic windows and held build/UI work during this sample. Other workstation activity was not controlled. Raw files remain in ignored validation artifacts.

Run using the repository's .NET 10 SDK:

```powershell
dotnet src/MyCapture.App/bin/Release/net10.0-windows10.0.22000.0/MyCapture.dll --selftest-pin-storage-performance artifacts/validation/pin-storage-verified
```

The workload creates generated images and an isolated queue beneath its output directory. It does not read the user queue or clipboard. The pin adapter invokes the actual WPF mouse-down/move/up overrides with synthetic input observations, retains the production per-gesture desktop cache, moves the real HWND, and verifies the final physical position and capture lifetime. It does not move the OS pointer. This measures callback service time; it excludes OS input queue and physical mouse latency. The idle process is the diagnostic host, not the fully initialized tray application.

## Next implementation boundary

Inspection found one required metadata write and one required index write for successful original publication, then a separate publication when OCR adds new information. No redundant same-generation index save was identified on those paths. Skipping unchanged OCR text would mostly improve this diagnostic's repeated-call workload, not the normal indexing path. Changing global atomic-file durability would affect unrelated recovery guarantees.

The baseline suggested immutable owner-thread serialization and ordered off-thread disk publication for original capture and OCR. It must share ordering with existing synchronous saves, await durable completion before clearing original pending markers, retain revision checks and owner-thread mutation, and propagate failures without promising a saved capture. The implementation and subsequent measurements follow below.

## Ordered publication implementation and failed first after sample

Commit `c0e65ec477adee79bec687c33cec84f9bf40a335` implements that follow-up. Every metadata/index save enters the same FIFO. Async original/OCR publication waits for one of eight reservations before owner-thread mutation/serialization, then sends immutable path/content pairs to the disk writer. Synchronous saves bypass reservation capacity but join the same FIFO and wait outside the ordering gate. This avoids a deadlock when reservations belong to continuations waiting for the owner dispatcher. Original publication holds busy/eviction protection and preserves its pending marker on failure; OCR rechecks revision/existence after admission and leases accepted writes against deletion. Existing final synchronous `Save()` drains accepted work. Finalize transaction call sites and atomic-file durability are unchanged.

Verification passed three Core publication tests and sixty App persistence/OCR/gallery tests, with zero failures/skips. These include mixed sync/async ordering, immutable generations, all slots reserved without any job yet submitted, failure followed by successful publication, original durability/notification, stale OCR after capacity wait, eviction protection, and final-save drain.

The first after attempt, `artifacts/validation/pin-storage-after-ordered-publication`, exited 1 and recorded `RESULT: FAIL`. Its completed report is timestamped `2026-09-08T15:13:53Z`. It recorded an unsuccessful OCR publication and then `IOException` from `File.Replace` during the first index save of the 300-record stage. Both original batches and the 32-record stage completed, but original wall medians were 7.4–7.9 seconds and the 32-record index-save median was 909 ms, versus approximately 29–34 ms and 7 ms in the baseline. This is not a valid before/after comparison.

The run overlapped possible test load and recurring host runner connection failures. Neither overlap proves the cause of the replacement failure. Subsequent read-only inspection found valid 32-record JSON in both `index.json` and its backup (17,247 bytes each, Node mode `100666`), no sibling temporary file, and approximately 802 GiB of available local volume capacity. The original report did not capture a numeric HRESULT, and its null OCR logger discarded the inner OCR exception, so that numeric result cannot be reconstructed honestly. The failure is preserved. The diagnostic now records HRESULT, queue size/sample, metadata path, and index/backup attributes, sizes and timestamps on failure; it adds no retry or durability change.

The updated diagnostic measures owner service through a forwarding dispatcher synchronization context. It times the initial call and its owner-context continuations, excluding time spent waiting for image/disk workers or pumping the harness dispatcher. Original owner service includes record creation and final marker cleanup, so it is broader than the baseline's publication-only UI interval. OCR reports both awaited wall time and owner service for the same sixteen uncoalesced publications at each queue size.

## Completed quiet after sample

`artifacts/validation/pin-storage-after-quiet` exited 0 and recorded `RESULT: PASS` at `2026-09-08T15:25:15Z`. All workers explicitly confirmed no builds/tests or native fixtures were active before the run and held that state through completion. Other workstation activity was not controlled. Source was `c0e65ec` plus the diagnostic observer/contextual failure logging included in this document's commit. No production behavior changed between the failed and successful after attempts.

The same generated image sizes, sequential sixteen-capture batches, and sixteen OCR publications per queue size ran successfully. Every original passed file/pending-marker checks, all OCR publication calls returned success, six text OCR results were `Success`, six blank results were `NoText`, and all six pin gestures retained capture with exact expected final HWND positions.

The original comparison is deliberately conservative about scope: the after owner interval also includes record creation, worker launch, marker cleanup and notification. The first cold 320 × 240 sample consumed 15.770 ms of owner service; this is retained rather than removed as an outlier. Metadata-through-notification awaited medians were 9.062/9.636 ms. The measured change frees the owner during disk waits; it is not an original-capture throughput or latency win.

Synchronous index-save median/p95 was 7.122/9.654 ms at 32 records, 8.302/10.089 ms at 300, and 8.743/10.628 ms at 1,000. Pin callbacks remained approximately 1.080–1.299 ms median, with p95 1.752–2.323 ms and the same approximately 30 ms median timer cadence. No pin speedup, total CPU reduction, or long-running tray-idle claim follows from this storage change.

The earlier `File.Replace` failure did not recur in this quiet sample. Its cause remains unresolved; passing this sample does not establish that the underlying failure is fixed. The original failed report, index and backup remain available for investigation, and future failures now retain contextual HRESULT evidence.
