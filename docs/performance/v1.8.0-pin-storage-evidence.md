# Pin lifecycle and storage measurements

Measured on 2026-09-08 with Release source based on `776da73`, plus the diagnostic added by this document's commit. The final run is `artifacts/validation/pin-storage-verified/pin-storage-performance.json`; its sibling report says `RESULT: PASS`, and the process exited 0. The lead closed its synthetic windows and held build/UI work during this sample. Other workstation activity was not controlled. Raw files remain in ignored validation artifacts.

Run using the repository's .NET 10 SDK:

```powershell
dotnet src/MyCapture.App/bin/Release/net10.0-windows10.0.22000.0/MyCapture.dll --selftest-pin-storage-performance artifacts/validation/pin-storage-verified
```

The workload creates generated images and an isolated queue beneath its output directory. It does not read the user queue or clipboard. The pin adapter invokes the actual WPF mouse-down/move/up overrides with synthetic input observations, retains the production per-gesture desktop cache, moves the real HWND, and verifies the final physical position and capture lifetime. It does not move the OS pointer. This measures callback service time; it excludes OS input queue and physical mouse latency. The idle process is the diagnostic host, not the fully initialized tray application.

The timer did not deliver a 16 ms cadence; dispatch gaps must not be presented as hardware mouse latency or 60 Hz proof. Mouse-down cost was 0.056–0.123 ms. Gesture process CPU ranged from 15.625 to 328.125 ms over 1.508–1.581 seconds; coarse CPU accounting includes the diagnostic dispatcher/render process, not only the callback. No before/after speedup is claimed.

Three hidden-idle samples each measured zero reported process CPU over approximately two seconds. Visible-idle samples reported 62.5, 0, and 0 ms CPU (0.196%, 0%, 0% normalized over 16 logical processors). All six allocated 1,360 bytes including the harness. The earlier `pin-storage-run1` first hidden sample included dispatcher startup; this final harness warms the dispatcher first. These short samples cannot establish long-running tray idle behavior.

The production lifecycle fix has separate focused coverage: 23 pin lifecycle/manager tests passed, including failed mouse capture, capture loss, button release without a delivered button-up event, native capture release, close cleanup, and a fresh gesture after cancellation.

## Persistence and OCR results

Sixteen sequential original captures at each size exercise the real image writer, metadata/index publication, pending-marker cleanup, and notification. Every original exists and every completed pending marker is gone. Publication is the synchronous interval from the existing pre-metadata hook through `ImagePersisted`.

| Synthetic original | Total median / p95 ms | UI publication median / p95 ms |
| --- | ---: | ---: |
| 320 × 240 | 28.963 / 94.175 | 8.976 / 10.735 |
| 1280 × 720 | 33.558 / 56.928 | 9.065 / 10.581 |

The table below uses sixteen real index writes and sixteen OCR metadata/index publications at each queue size. The larger queues contain generated metadata records. These repeated OCR calls measure the publication path; they are not a claim that normal indexing republishes an unchanged result repeatedly.

The earlier run's 1,000-record index p95 was 73.389 ms; the final sample's 13.166 ms demonstrates tail variability. With sixteen samples, nearest-rank p95 is the maximum. Neither run proves a stable tail-latency distribution.

Windows OCR uses generated 720 × 360 text/blank PNGs, the production indexing mode without orientation search, and six samples each. All text samples returned `Success` and recognized the expected text; all blank samples returned `NoText`. Text wall median/p95 was 115.475/208.065 ms (reported pipeline 99.888/202.349 ms); blank wall median/p95 was 91.305/123.873 ms (pipeline 78.588/120.684 ms). This background work is slower than publication overall, but the synchronous owner-thread publication is the directly measured UI stall.

## Next implementation boundary

Inspection found one required metadata write and one required index write for successful original publication, then a separate publication when OCR adds new information. No redundant same-generation index save was identified on those paths. Skipping unchanged OCR text would mostly improve this diagnostic's repeated-call workload, not the normal indexing path. Changing global atomic-file durability would affect unrelated recovery guarantees.

A useful bounded follow-up is immutable owner-thread serialization and ordered off-thread disk publication for original capture and OCR. It must share ordering with existing synchronous saves, await durable completion before clearing original pending markers, retain revision checks and owner-thread mutation, and propagate failures without promising a saved capture. This document records a baseline; it does not assert that this follow-up is implemented or faster.
