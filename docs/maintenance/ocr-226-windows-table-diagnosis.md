# #226 Windows OCR 한국어 표 진단

2026-11-06, 브랜치 `fix/windows-ocr-table-226`(기준 `d28e9172`). Windows 11 26200, Windows OCR 인식 언어 `ko` 하나(`MaxImageDimension` 10000), .NET 10.0.12, 맑은 고딕 `MALGUN.TTF` 6.69(SHA256 `7A183CF1C6C56B9609FCC16EDA8B5229FBC11758A21E669EC00343239B02192F`).

## 결론

`Ocr410WindowsEngineTests`의 한국어 표 단정 2개는 시험한 전처리(배율·보간·대비·굵게·이진화·여백·DPI·글자 렌더링)로 정당하게 통과시키지 못했습니다. 두 실패 모두 엔진의 글자 줄 검출에서 생깁니다. Windows OCR 전처리 코드는 바꾸지 않았고 시험 단정도 그대로 두었습니다.

기본 설정인 빠름은 Windows OCR만 쓰므로 사용자는 이 실패를 그대로 봅니다. 정확 모드에서 신경망 모델을 쓰면 고정 표의 `항목`·두 금액·3열×4행·머리글을 모두 맞힙니다. 표 탭(표 핀이 복사하는 TSV)은 신경망 단독 결과가 가장 정확했고, 병합 결과는 숫자 중복 때문에 그보다 떨어졌습니다. 격자 표에서는 신경망 상자가 글자보다 커서 수량과 금액이 한 칸으로 합쳐지는 문제가 둘 다에 있습니다([제품 경로와 엔진 비교](#제품-경로와-엔진-비교)).

리드 결정으로 정확 모드(모델 있음)에 세 가지를 적용했습니다. 표 탭을 신경망 표로 만들고 빈 칸만 병합 칸으로 메우는 것(A), 병합 결과에서 같은 자리의 같은 글자를 한 번만 남기는 것(D), 표 탭의 열 간격 판단에서만 신경망 상자의 여백을 빼는 것(C)입니다. 합성 828개에서 보이는 결과의 편집 수는 2349→1690(차이 -659, 95% 구간 -904..-441), 표 탭으로 열리는 표본의 TSV CER은 6.43%(157개)→1.84%(164개), 글자 탭 편집 수는 2826→2567, 숫자 중복은 37개→2개가 되었습니다. OCR을 더 돌리지 않고, 세 가지가 더하는 후처리 시간은 표본 중앙값 0.008 ms, 최대 0.093 ms입니다([적용한 변경과 측정](#적용한-변경과-측정2026-11-07)).

합성 자료 828개에서 전처리 후보 8개를 현재 제품과 짝지어 비교했습니다. 고정 표의 서비스 단정을 통과시킨 후보는 없었고, 세 자료 모두에서 편집 수가 줄어든 후보도 없었습니다(쌍삼차 보간도 잡음 층에서 +14입니다). 한국어 표 층에서는 모든 후보가 현재 제품과 같거나 나빴습니다.

- 원해상도 탐침(`OriginalResolutionProbe("table")`): 머리글 `항목 수량 금액`의 단어 상자 높이가 12px(y 40–52)입니다. 엔진은 음절의 윗부분(초성과 중성)만 한 줄로 잡고 받침 줄(y 52–61)은 버립니다. 그래서 `항목`은 읽히지 않고 `수량`은 `` -`卍들 ``, `금액`은 `그에`가 됩니다.
- 자동 4배 경로(`InstalledWindowsEngineRecognizesIsolatedExtractionExamples("table")`): 같은 받침 줄을 `O 그`, `丁 O` 같은 별도 줄로 읽습니다. `1,204,000`은 엔진이 쉼표를 찾지 못해 `1`·`204`·`000` 세 단어가 됩니다. 쉼표 손실은 2.5배부터 나타납니다.
- 이슈 원본(Windows 10 19045)과 이 PC의 4배 원문이 같습니다(`öh모`, `기보드`, `IJSB 케이블`, `1 204 000`).

## 넓은 자료 비교

자료 세 가지를 썼습니다. 모두 합성 글자만 담았습니다.

- `commercial-synthetic-300-v1`: 기존 생성기로 이 PC에서 만든 300개입니다. 한글·영문·혼합·작은 글자·코드 5종이며, 190개는 자동 3배, 110개는 자동 4배 구간입니다.

- `ocr226-clutter-192-v1`(새로 만듦): 격자 표·입력 상자·아이콘과 강조 행이 있는 목록·도구 막대 4종 × 9~40px 12단계 × 밝음/어두움 × 자르기입니다. 분할 규칙은 층화 자료와 같습니다.

측정은 서비스의 빠름 경로(자동 배율, 회전 탐색 없음, 줄 만들기와 언어 병합)를 따르는 진단 시험으로 했습니다. 진단 시험의 기준값 `adaptive-nn`은 제품 경로 `OcrCommercialCorpusTests.MeasureFast`와 300개 표본 모두 원문이 같았습니다(CER 4.10%, 줄 누락 26/996). 검토 수정 뒤 다시 잰 실행의 `adaptive-nn`은 세 자료 828개 모두 제품 빠름 경로([엔진 비교](#제품-경로와-엔진-비교)의 `fast`)와 원문이 같습니다. 첫 실행은 층화 자료 2개(`table-ko-10-light-wide`, `table-ko-12-light-wide`)에서 같은 단어를 한 줄로 이을지만 제품과 달랐습니다.

표의 dEdits는 기준 대비 표본별 문자 편집 수 차이의 합이며, 음수가 나아진 것입니다. 괄호는 표본 부트스트랩 95% 구간입니다. 시간은 전처리와 인식을 합한 값입니다. 각 표의 위 묶음은 첫 실행이고 기준은 첫 실행의 `adaptive-nn`입니다. 쌍삼차 보간은 검토에서 투명도를 흰 배경에 합성하지 않고 보간한 오류를 찾아 고친 뒤 다시 쟀습니다. 아래 묶음이 그 실행이며, 같은 실행에서 잰 `adaptive-nn`을 기준으로 삼았습니다. 그 행의 dEdits만 첫 실행 기준과의 차이입니다. `adaptive-nn+opaque`는 같은 실행에서 불투명화만 한 대조군입니다. 측정하는 동안 다른 세션의 testhost가 첫 실행에는 4~5개, 다시 잰 실행에는 5~11개 함께 돌았습니다. 그래서 같은 기준의 평균 시간도 135 ms에서 184 ms로 늘었고, 시간은 같은 실행 안의 상대 비교로만 봅니다.

- 쌍삼차 보간(`adaptive-bicubic`): 기존 300개 -45, 층화 -72로 조금 낫고 잡음 층은 +14이며, 세 구간 모두 0을 지납니다. 한국어 표 층에서는 +44(구간 +3..+94)로 나빠지고, 잡음 층의 줄 누락이 1개에서 3개로 늘었습니다.

- 글자 높이 기반 배율(`t40`~`t56`): 줄 높이를 목표 픽셀로 맞추되 자동 배율을 넘지 않게 합니다. 깨끗한 두 자료에서는 정확도가 같거나 조금 낫고 평균 시간이 22~44% 줄며, `t48-bicubic`은 기존 300개 -117(-179..-60)과 층화 -120(-239..-10) 모두 구간이 0 아래입니다. 그러나 격자 표에서 세로 격자선 때문에 표 전체를 한 줄로 재어 배율이 1배로 떨어집니다(잡음 층 +326~+499, 줄 누락 1개에서 26~34개). 한국어 표 층도 `t48-bicubic` +45(+3..+86)로 나빠집니다.

## 제품 경로와 엔진 비교

### 기본 설정에서 보이는 결과

- 설정 기본값은 빠름입니다(`AppSettings.cs` `OcrSettings.Quality`). 빠름과 균형은 Windows OCR만 씁니다. 이 PC에서 균형은 표 자료 104개 모두 빠름과 원문이 같았습니다.
- 첫 실행 창은 논리 CPU 4개·메모리 8 GB 이상이고 절전 모드가 아니면 정확을 미리 골라 둡니다. 그대로 닫으면 정확으로 바꾸고 모델 약 102 MB(인식기·사전·서버 검출기)를 내려받습니다(`FirstRunOcrChoice`).
- 정확은 모델이 있으면 Windows 빠름 경로와 신경망(PP-OCRv5)을 함께 돌려 `OcrResultMerger.Merge`로 합칩니다(`CaptureOcrService.RecognizeDualAsync`). 모델이 없으면 Windows만 4배·대비·회전 탐색으로 읽습니다.
- 결과 창은 표 구조와 숫자 열이 있으면 표 탭으로 열립니다(`OcrResultWindow.Advanced.cs` `ApplyAdvancedResult`). 표 탭에서 핀을 만들면 표의 TSV가 핀 원문이 됩니다(`OcrResultWindow.Pin.cs` `RequestPinAsync`). 그래서 표→핀→원문 붙여넣기에서 사용자가 받는 것은 글자 결과가 아니라 표 재구성 결과입니다.

정리하면 빠름 사용자는 #226의 `항목` 누락과 `1 204 000`을 그대로 봅니다. 정확을 고르고 모델을 받은 사용자는 병합 결과를 봅니다.

  - 금액 칸: 천 단위 쉼표가 있는 정답 칸 중 같은 칸으로 맞춘 수

### 판단

- 모델이 있으면 #226의 고정 표는 신경망 단독과 병합 모두에서 `항목`·두 금액·3열×4행·머리글을 맞힙니다. 빠름·균형·정확(모델 없음)은 맞히지 못합니다.
- 한국어 표 층의 표 탭은 신경망 단독이 가장 정확하고, 병합은 숫자 중복 때문에 그보다 떨어집니다. 글자 탭은 병합이 15개 범주 중 11개에서 빠름보다 확실히 편집 수가 적습니다(95% 구간이 0 아래). 구간이 0을 지나는 범주는 `form-ko` -72 (-158..+7), `grid-ko` +12 (-73..+108), `small` -9 (-48..+27), `table-en` -123 (-321..+68)입니다. 나빠진 범주는 없습니다.
- 계산을 더 하지 않고 얻는 가장 큰 개선은 정확 모드의 표 탭을 신경망 표로 만들고 빈 칸만 병합 칸으로 채우는 것입니다(전체 -427, 95% 구간 -636..-256). 빠름 모드에서 한국어 표에만 신경망을 한 번 더 돌리면 개선이 더 크지만(전체 -669, 95% 구간 -857..-496) 발동할 때마다 시간·CPU·메모리가 더 듭니다.
- 격자 표의 금액 칸은 신경망 상자 높이 때문에 지금은 빠름보다 나쁩니다. 이 문제를 먼저 풀어야 신경망 표를 앞세우는 규칙이 격자 표에서 손해를 보지 않습니다.
- 이 비교는 모두 합성 글자(맑은 고딕 렌더)이고, Windows OCR 인식 언어가 `ko` 하나인 PC에서 잰 값입니다. 실제 캡처 표본으로 다시 확인해야 합니다.

## 다시 돌리는 방법

진단 시험은 기본으로 건너뜁니다. 출력과 자료 경로는 저장소 `artifacts\` 아래의 절대 경로여야 합니다.

| `MYCAPTURE_OCR226_RUN` | 하는 일 | 추가 변수 |
| --- | --- | --- |
| `fixture` | 고정 표의 단계별 기록(배율 8단계 × 보간 4종 × 3회) | |
| `explore` | 고정 표에 화소 연산 적용 | `MYCAPTURE_OCR226_CONFIGS`(선택) |
| `render` | 같은 표를 글자 렌더링·DPI만 바꿔 읽기 | |
| `generate` / `generate-clutter` | 층화 336개 / 잡음 층 192개 생성 | |
| `sweep` | 자료에 전처리 후보 적용, 고정 표의 서비스 단정도 함께 기록 | `MYCAPTURE_OCR226_CORPUS`, `MYCAPTURE_OCR226_CONFIGS`, `MYCAPTURE_OCR226_SPLIT` |
| `estimate` | 줄 높이 추정기 두 가지만 비교(인식 없음) | `MYCAPTURE_OCR226_CORPUS`(쉼표로 여러 개) |
| `engines` | 제품 경로 다섯 가지(빠름·균형·정확 모델 없음·신경망 단독·병합)로 자료와 고정 표를 읽고 시간·메모리를 기록(`Ocr226EngineComparisonTests.Compare`) | `MYCAPTURE_OCR226_CORPUS`(쉼표로 여러 개), `MYCAPTURE_OCR226_CATEGORIES`, `MYCAPTURE_OCR226_PATHS`, `MYCAPTURE_OCR_LIVE_MODELS` |

모든 모드는 `MYCAPTURE_OCR226_OUTPUT`에 새 폴더를 만들어 결과를 씁니다.

```bat
set MYCAPTURE_OCR226_RUN=sweep
set MYCAPTURE_OCR226_CORPUS=%CD%\artifacts\ocr226\strata336
set MYCAPTURE_OCR226_OUTPUT=%CD%\artifacts\ocr226\sweep-01
set MYCAPTURE_OCR226_CONFIGS=adaptive-nn,adaptive-bicubic,t48-nn
dotnet test tests\MyCapture.App.Tests\MyCapture.App.Tests.csproj -c Release --no-build --filter "FullyQualifiedName=MyCapture.App.Tests.Ocr226PreprocessingDiagnosticTests.Observe"
```

구성 이름은 `<배율>-<보간>[+<연산>]`입니다. 배율은 `adaptive`(제품 규칙), `s<배수>`(고정), `t<목표>`(줄 높이를 목표 픽셀로, 자동 배율 이하), `T<목표>`(4배 이하), `r<목표>`(t와 같되 얇은 세로선 제외)입니다. 보간은 `nn`·`linear`·`fant`·`bicubic`, 연산은 `opaque`·`gray`·`otsu`·`gamma2`·`min3`입니다.

기존 300개는 `MYCAPTURE_OCR_COMMERCIAL_RUN=generate`와 `MYCAPTURE_OCR_COMMERCIAL_OUTPUT`을 두고 `OcrCommercialCorpusTests.GenerateSynthetic300`으로 만듭니다. 기준값을 제품 경로와 맞춰 보려면 같은 자료로 `MYCAPTURE_OCR_COMMERCIAL_RUN=full-fast`, `MYCAPTURE_OCR_COMMERCIAL_CORPUS`, `MYCAPTURE_OCR_COMMERCIAL_OUTPUT`을 두고 `OcrCommercialCorpusTests.MeasureFast`를 실행한 뒤, 표본별 원문을 `sweep`의 `rows.json`(`adaptive-nn`)과 비교합니다.

- 제품 측 완화는 2026-11-06 리드 결정으로 세 가지를 적용했습니다. 정확 모드의 표 탭을 신경망 표로 채우고 빈 칸만 병합 칸으로 메우기(A), 병합 결과의 같은 자리 중복 제거(D), 열 간격 판단에서만 신경망 상자 여백 빼기(C)입니다([적용한 변경과 측정](#적용한-변경과-측정2026-11-07)). A에서 나빠진 표본 6개(띄어쓰기 5개, 칸 앞 기호 1개)는 리드 결정으로 받아들였습니다.
- 빠름 모드에서 한국어 표에만 신경망을 더 돌리는 경로(B)는 사용자 결정이라 #223 결과 뒤 다시 정합니다. 결정 전 숫자는 [제품 경로와 엔진 비교](#제품-경로와-엔진-비교)에 있습니다.
