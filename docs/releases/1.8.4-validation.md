# 1.8.4 capture latency and memory validation

Status: v1.8.4 published as the latest stable release. Base: `abffc6398ef16ab8b29f9b7db5deb3fc029be638` (v1.8.3). This completion record was added after publication; the immutable package source is recorded below.
Task branch: `agent/capture-latency-memory-1.8.4`.

Scope: remove the blank opaque selector shown before capture acquisition completes; reduce pointer rendering allocations; release unnecessary full-desktop image ownership and unreachable editor image assets. Preserve capture coordinates, Shift precision, undo/redo, original capture persistence, and normal recording selection. User requested fixes and deployment; release actions are authorized.

## Investigation

- Both still and recording coordinators show a black, opaque, frame-less selector when capture exclusion succeeds. Keep the HWND hidden until the acquired background is attached.
- The editor stores a full-desktop `FrozenFrame` solely for commit metadata even though its surface uses the independent selection crop. Replace that ownership with pixel-free metadata.
- Inserted-image assets have no pruning when history branches are discarded or history reaches its limit. Retain the union of live document and reachable undo/redo assets.
- The selector recreates background drawing commands and magnifier crops during pointer movement. Split retained background and transient visuals and reuse magnifier pixels.
- AGY read-only run `07148aed-80d4-4746-bf01-6bb536aadde4` completed successfully at the clean base. Its findings are hypotheses, independently checked before implementation. In particular, the claim that completed async test Tasks necessarily retain their full state machines was rejected: [.NET 10 clears completed state-machine boxes](https://github.com/dotnet/runtime/blob/v10.0.0/src/libraries/System.Private.CoreLib/src/System/Runtime/CompilerServices/AsyncTaskMethodBuilderT.cs).
- Resident process at investigation start: working set 156,282,880 bytes, private memory 132,091,904 bytes. This does not reproduce the user's reported 1 GB state; no real captures or private queue contents were inspected.
- A subsequent native-memory investigation found that short-lived `StaThreadTask` workers exited without shutting down their lazily created WPF Dispatcher. WPF's [MediaContext teardown](https://github.com/dotnet/wpf/blob/main/src/Microsoft.DotNet.Wpf/src/PresentationCore/System/Windows/Media/MediaContext.cs) runs on `ShutdownFinished` and releases notification windows and rendering channels. The helper now shuts down only its existing worker Dispatcher before completing the returned task, including failure paths. Frozen bitmap results remain usable after teardown.

## Local verification and measurement

- Same diagnostic source SHA-256 on both sides: `569cb627cfeb3b21b5f33b93d71bcb12d1b08f18786670c894e48a2b2960ab91`. Baseline is the base commit plus only the diagnostic and CLI registration, built in a separate disposable worktree. Fixed source contains the reviewed changes on the task branch. Separate Release processes, same Windows desktop session, WPF rendering tier 2.
- Command: `dotnet MyCapture.dll --selftest-capture-performance <isolated-output-directory>`. Actual test outputs are `artifacts/validation/1.8.4/baseline-idle` and `fixed-idle`. Both exited 0 with functional lifecycle PASS. Summary: `final-comparison.json`.
- Fixture: 3840×2160 fresh native-backed synthetic image; 150 ms injected acquisition delay; real visible selector; 640×480 crop and editor; isolated original PNG persistence each round; Done every fifth round with a non-publishing clipboard sink. Two warm-up rounds, 20 measured rounds, then ten seconds of natural idle. Pointer stream: 300 ms per round, 8 ms timer, eight injected pointer updates per callback. An initial native cursor placement exercises real magnifier visibility; conditional restoration respects user movement.
- All measured callbacks were inside the selector (baseline 385/385; fixed 398/398). Totals differ because the timer is wall-clock bounded, so allocations are normalized per update. No forced collection or working-set trimming occurred before the idle samples. A separate post-soak forced collection audit found zero remaining tracked window/editor/bitmap objects in both versions; this is not a production memory-reclamation technique.

The significant measured effects are removal of the visible frame-less preparation interval, about 90% lower input-handler allocations, and reduced handle growth (403 versus 105). Peak/idle RAM did **not** show a large, consistent reduction; both versions released much of their native working memory during idle. The user's persistent 1 GB condition was not reproduced by this final fixture. Full-resolution images and active undo history still require memory. WPF scheduling observations do not prove physical mouse-to-display latency or actual DWM black pixels; no universal flicker/performance claim is made.

Earlier investigations remain separate: the 7680px fixture failed the machine's physical-window size limit; the first 4K run did not cover magnifier visibility; an earlier image generator allocated an extra full-frame managed array and produced higher peaks near 1 GB. Those exploratory runs are retained under `artifacts/validation/1.8.4` and are not mixed into this comparison. A new cleanup test initially ran before Loaded/first render and was corrected to await readiness while preserving all cleanup assertions. Two new STA tests triggered xUnit's blocking-task analyzer and were converted to async awaits without suppressions.

Independent product review: `independent_review` found no blocker in renderer/metadata/undo changes and the subsequent STA cleanup, including bitmap consumers and clipboard materialization. `export_implementation` separately reviewed coordinator startup/cancellation/exclusion changes. The lead inspected patches and diagnostic amendments. No worker test claim substituted for executed verification.
