# MyCapture 1.8.1

> 이 문서는 패치의 변경 범위를 설명합니다. 실제 배포 커밋·파일·검증 결과는 [GitHub 릴리스](https://github.com/sukwoo0711-maker/my-capture/releases)의 검증 기록을 확인하세요.

1.8.1은 영역 캡처 단축키를 누르는 순간 발생하는 멈춤 현상을 다룹니다. 기존 경로에서는 선택 화면을 열기 전에 전체 가상 데스크톱의 픽셀을 UI 스레드에서 동기적으로 읽었습니다. 이 과정에서 큰 임시 이미지 버퍼를 할당하고 복사하는 비용도 확인했습니다.

- 전체 데스크톱 이미지 획득을 작업 스레드로 옮겨, 캡처 준비 중에도 UI 디스패처가 다른 입력과 화면 작업을 처리할 수 있게 했습니다. 선택 화면은 새로 획득한 고정 이미지가 준비된 뒤에 표시합니다.
- 화면 픽셀을 WPF 비트맵의 잠긴 버퍼로 직접 읽습니다. 전체 화면 크기의 관리형 임시 배열과 추가 복사를 제거하고, 읽기가 완료된 비트맵만 잠금을 해제하고 고정해 전달합니다.
- 단축키를 연속으로 눌러도 동시에 하나의 캡처만 준비합니다. 취소 후에는 진행 중인 네이티브 캡처가 끝날 때까지 새 캡처를 막고, 늦게 도착한 결과를 버립니다. 앱 종료 후에도 선택 화면이 다시 열리지 않습니다.
- 이미지 획득 실패는 UI에서 알리고 다시 시도할 수 있습니다. 녹화 중 캡처 제외 처리는 선택 화면을 표시하기 직전에 다시 확인합니다.
- 캡처 요청, 이미지 획득 완료, 선택 화면의 첫 렌더링 시간을 로그에 기록합니다. 이미지 픽셀이나 사용자 텍스트는 이 진단 로그에 기록하지 않습니다.

로컬 4806×2466 가상 데스크톱에서 첫 획득 이후 변경 전후 각각 5회 측정한 이미지 획득 시간 중앙값은 **110.791ms → 81.285ms**, 호출 스레드의 관리형 할당량 중앙값은 **47,408,472바이트 → 1,880바이트**였습니다. 할당량에는 네이티브 이미지 메모리가 포함되지 않습니다. 별도의 첫 획득 측정은 앱의 사전 준비 작업을 실행하지 않은 새 프로세스에서 수행했으므로 일반적인 상주 앱의 첫 단축키 응답 시간과 같지 않습니다.

실제 캡처를 포함한 디스패처 진단은 변경 전후 각각 3회 수행했습니다. 요청 간격 16ms의 타이머가 캡처 중 처리한 틱은 각 실행에서 **0회 → 4회**, 최대 틱 간격은 **99.111–103.194ms → 31.556–35.814ms**였습니다. 이는 캡처 중 UI 작업을 처리할 수 있게 된 결과이며, 일정한 16ms 응답이나 시스템 전체의 멈춤 해소를 뜻하지 않습니다.

이미지 획득 측정에서 각 샘플의 Gen0·Gen1·Gen2 수집 횟수 증가는 변경 전후 모두 각각 1회로 같았습니다. 별도 디스패처 진단의 최근 GC 일시 중지 지표는 1ms 미만이었지만, 전체 실행에 발생한 모든 일시 중지 시간의 합계가 아닙니다. GC 감소나 전체 CPU 사용량 개선을 주장하지 않습니다.

하나의 STA 앱·디스패처를 유지한 실제 코디네이터 진단에서도 3회 캡처, 선택 화면 첫 렌더링, 취소, 알려진 색상으로 다시 그리기를 통과했습니다. 요청부터 첫 렌더링까지는 **279.778 / 160.939 / 168.422ms**였습니다. 이 로컬 진단 결과와 최종 커밋의 전체 테스트·패키지·배포 검증은 별개입니다. 상세 측정 조건과 남은 검증 절차는 아래 검증 문서에 기록합니다.

Windows 지원 범위, 오프라인 설치·포터블 배포, 기존 캡처·편집 데이터 형식은 [1.8.0](1.8.0-release-notes.md)의 범위를 유지합니다. 패치 검증 절차는 [1.8.1 검증 문서](1.8.1-validation.md)에 설명합니다.

## English overview

The region-capture hotkey previously acquired the entire virtual desktop synchronously on the UI thread, with a large temporary image allocation and copy. Frame acquisition now runs on a worker thread while a single active session prevents overlapping requests. Cancellation and shutdown discard late results; failure feedback and recording-exclusion checks remain on the UI dispatcher.

Direct readback now writes into the locked WPF bitmap buffer, removing the full-frame managed staging array and extra copy. Five warm acquisition samples per version on a 4806×2466 desktop measured median acquisition time of 110.791 → 81.285ms and calling-thread managed allocation of 47,408,472 → 1,880 bytes; unmanaged image surfaces are excluded. Cold samples omit resident-app prewarm. GC collection increments were unchanged.

In three actual-capture dispatcher samples per version, a timer requesting 16ms intervals delivered 0 → 4 ticks during capture, with maximum gaps of 99.111–103.194 → 31.556–35.814ms. Its latest GC pause metric was below 1ms, not a sum of every pause. Three real coordinator capture/render/cancel/repaint cycles also passed with one persistent STA owner; request-to-render samples were 279.778, 160.939, and 168.422ms. These local diagnostics do not claim elimination of system-wide stutter or completion of the final exact-source release gates.
