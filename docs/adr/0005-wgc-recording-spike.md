# ADR 0005 — Windows Graphics Capture 녹화 백엔드 스파이크

상태: 스파이크 측정 완료, 미채택(조건부 진행 권고)
기준: `67bc397`, 브랜치 `spike/wgc-recording`(통합 브랜치에 병합하지 않는다)
관련: [ADR 0002](0002-region-recording.md)(GDI BitBlt 채택), [경쟁 매트릭스 P0](../competitive-matrix.md#다음-우선순위),
[v1.8.0 녹화 캡처 증거](../performance/v1.8.0-recording-capture-evidence.md)

## 배경

ADR 0002는 녹화 프레임 그랩에 정지 캡처와 같은 GDI `BitBlt + CAPTUREBLT` 경로를 재사용했다. D3D 장치와
복제 세션 없이 실패 표면을 작게 유지하려는 결정이었다. 현재 `RegionFrameGrabber`는 녹화 스레드(MTA,
BelowNormal)에서 `ScreenCaptureEngine.CaptureSession`으로 영역을 CPU 비트맵에 복사하고 `GetDIBits`로
BGRA 버퍼를 만든 뒤 Media Foundation H.264 인코더에 넘긴다. 녹화 컨트롤 창, 선택기, 편집기는
`SetWindowDisplayAffinity(WDA_EXCLUDEFROMCAPTURE)`로 제외하고 녹화 시계는 의도적으로 포함한다.

경쟁 매트릭스 P0는 Windows Graphics Capture(WGC) 또는 Desktop Duplication 백엔드를 "현재 GDI 경로 대비
1080p/4K에서 CPU, 프레임 드롭, 복구가 계측상 개선되고 Windows 11 22000 실기기 통과" 조건으로 승격한다.
이 스파이크는 WGC를 같은 프레임 계약에 붙여 같은 PC, 같은 영역에서 측정하고 진행 여부를 권고한다.

## 스파이크 구현

| 항목 | 내용 |
|---|---|
| 선택 | 내부 환경 변수 `MYCAPTURE_RECORDING_BACKEND=wgc`. 다른 값이나 미설정은 GDI. 설정 파일·UI에 노출하지 않는다(`RecordingCaptureBackendSelection`). |
| 공급자 | `WgcRegionCaptureSession`: `IGraphicsCaptureItemInterop.CreateForMonitor` → `D3D11CreateDevice`(하드웨어, 실패 시 WARP, BGRA 지원) → `CreateDirect3D11DeviceFromDXGIDevice` → `Direct3D11CaptureFramePool.CreateFreeThreaded`(B8G8R8A8, 버퍼 3개) → 프레임 텍스처에서 녹화 영역만 `CopySubresourceRegion`으로 스테이징 텍스처에 복사 → `Map` 후 행 단위로 BGRA 버퍼에 복사. |
| 계약 | `RegionFrameGrabber.GrabInto()`의 짝수 폭·높이, 재사용 버퍼, 상단부터 BGRA 계약은 그대로다. `RegionRecorder`, 인코더, 일시정지 타임라인은 수정하지 않았다. |
| 프레임 풀 | `FrameArrived`에서 새 프레임을 받을 때마다 이전 프레임을 즉시 반납하고 최신 한 장만 보관한다. 일시정지나 인코딩 지연 중에도 풀이 차지 않으므로 DWM이 새 프레임을 버리지 않고, 보관한 프레임은 항상 현재 화면이다. |
| 정지 화면 | DWM은 내용이 바뀔 때만 프레임을 보낸다. 새 프레임이 없으면 직전 프레임이 담긴 버퍼를 그대로 쓴다(`ReusedCalls`). |
| 세션 열기 | `Open()`에서 작업 스레드로 세션 생성을 시작해 인코더 초기화(약 420~520ms)와 겹친다. 첫 `GrabInto`는 남은 시간만 기다린다(5초 초과 시 GDI). 처음 시도한 지연 생성 방식은 세션 생성 70~305ms가 녹화 타임라인 안에 들어가 3초 클립에서 6~17% 드롭을 만들었다. |
| 커서 | `IsCursorCaptureEnabled = IncludeCursor`. 커서 강조 링은 WGC가 그리지 않으므로 GDI와 같은 반지름(13/18), 두께(3/5), 색으로 관리 코드에서 그린다. |
| 테두리 | `GraphicsCaptureAccess.RequestAccessAsync(Borderless)` 결과를 프로세스당 한 번 캐시하고 `IsBorderRequired = false`를 설정한 뒤 읽어 진단값으로 남긴다. |
| 폴백 | 열기 단계: WGC 미지원, 영역이 한 디스플레이 안에 없음(여러 모니터에 걸침), 장치·항목 생성 실패, 5초 초과. 녹화 중: `Map` 실패(장치 제거 사유 포함), 디스플레이 제거(`GraphicsCaptureItem.Closed`), 해상도 변경으로 영역이 화면 밖으로 나감. 모두 그 녹화의 나머지를 GDI로 이어 가며 `FallbackReason`과 로그에 남긴다. |
| 의존성 | 새 NuGet·네이티브 바이너리 없음. `d3d11.dll`, `dxgi.dll`, `combase.dll` P/Invoke와 vtable 함수 포인터, OCR에 이미 쓰는 Windows SDK 투영(`Microsoft.Windows.SDK.NET`, `WinRT.Runtime`)만 사용한다. |

## 측정 환경과 방법

- PC: AMD Ryzen 7 9800X3D(8코어 16스레드), RAM 62GB, NVIDIA GeForce RTX 5080(드라이버 32.0.16.1088),
  디스플레이가 연결되지 않은 AMD Radeon 내장 GPU, Windows 11 Home 10.0.26200.
- 디스플레이: DISPLAY1 3440x1440 119Hz(주 모니터), DISPLAY2 768x1366 가상 디스플레이(Easy&Light Display HUB).
  DXGI `GetDesc1` 기준 두 출력 모두 SDR(ColorSpace 0 = G22/P709, 8bpc)이다. **HDR 모드가 켜진 디스플레이가 없어
  HDR은 측정하지 못했다.** 4K(3840x2160) 디스플레이도 없어 최대 측정 영역은 3440x1440이다.
- 부하: 다른 에이전트 팀이 같은 PC에서 빌드·테스트를 동시에 실행했다. 표본별 시스템 CPU는 18~93%였다.
  녹화 없이 합성 화면만 띄운 상태는 프로세스 CPU 0.85~0.89%, DWM CPU 0.67~0.94%, 시스템 GPU 3D 5.6~5.8%였다.
- 명령: `MyCapture.exe --selftest-recording-backends <절대 경로>`(`MYCAPTURE_BENCH_SECONDS=10`,
  `MYCAPTURE_BENCH_REPEATS=2`)를 두 번 실행해 칸마다 n=4다. 백엔드 순서는 쌍마다 번갈았다.
- 장면: 주 모니터 전체를 덮는 최상위 합성 창에서 흰 막대와 주황 상자가 매 합성 프레임 움직인다(WPF 약 60Hz).
  영역은 주 모니터 왼쪽 위 기준, 커서 미포함, 인코더 기본 비트레이트. 이 장면은 WPF 렌더 루프를 계속 돌려 녹화
  루프의 `Thread.Sleep`이 1ms 단위로 깨어나는 조건이다. 렌더 루프가 없을 때의 차이는 아래 "별도 발견"에 따로 적었다.
- 지표: "정상 구간"은 첫 프레임 인코딩 후 10초 창이다. 캡처 시간은 `GrabInto` 1회 소요다. CPU는 기존 방식대로
  CPU ms / 벽시계 ms / 논리 프로세서 16 × 100이다. DWM CPU는 PDH `\Process(dwm)\% Processor Time`(일반 사용자
  토큰으로 `Process.TotalProcessorTime`을 읽을 수 없음), GPU 3D는 모든 프로세스의 `\GPU Engine(*engtype_3D)` 합계다.
  메모리는 녹화 시작 직전 GC 후 사설 메모리 대비 녹화 중 최대 증가량이다. MP4는 디코드 확인 후 삭제했다.

해석:

- **60fps**: GDI는 BitBlt 한 번이 21~27ms로 16.7ms 예산을 넘어 2560x1440과 3440x1440에서 31~35fps(드롭 41~48%)에
  머문다. WGC는 같은 조건에서 58.6~59.2fps(드롭 1.3~2.4%)를 유지한다. 1080p60은 GDI도 대체로 따라가지만 부하가
  오르면 53.5fps까지 떨어졌다.
- **30fps**: 두 백엔드 모두 목표를 지킨다. 다만 GDI는 프레임 간격 33ms 중 14~25ms를 캡처에 쓰고 WGC는 0.8~1.7ms를
  쓴다. 느린 PC에서 GDI의 여유가 먼저 사라진다.
- **CPU**: 30fps에서 WGC가 프로세스 CPU를 0.8~1.9%p(16스레드 기준, 0.13~0.30코어) 낮춘다. 60fps 고해상도에서는
  프로세스 CPU가 비슷하지만 WGC가 1.7~1.9배 많은 프레임을 인코딩하므로 프레임당 CPU는 약 절반이다. DWM CPU는
  1.8~2.6%에서 0.9~1.1%로 줄고, 시스템 GPU 3D 사용률은 0.8~2.5%p 늘어난다(GPU 복사와 DWM 프레임 전달).
- **인코딩이 새 병목**: 프레임당 인코딩은 1080p 1.9~2.7ms, 1440p 3.5~4.4ms(부하 표본 하나 6.7ms),
  3440x1440 5.1~6.3ms로 두 백엔드가 같은 범위다. WGC 60fps에서는 캡처보다 인코딩(BGRA 전달·색 변환 포함)이 프레임 예산을 더 쓴다.
- **시작 지연**: `Start()`부터 첫 프레임 인코딩까지 평균은 두 백엔드 모두 약 470~580ms이며 MF 인코더 초기화가
  대부분이다. WGC 세션 생성은 61~123ms(프로세스 첫 세션 116~123ms, 이후 61~105ms)이고 인코더 초기화와 병렬이어서 첫 `GrabInto`의
  대기는 0.0~0.1ms였다.
- **메모리**: 녹화당 사설 메모리 증가는 GDI 46~138MB, WGC 59~129MB로 MF 인코더 할당이 지배해 차이를 판단할 수 없다.
  WGC는 이와 별도로 스테이징 텍스처(1080p 8.3MB, 1440p 14.7MB, 3440x1440 19.8MB)와 모니터 크기 풀 버퍼 3장
  (3440x1440 기준 약 59MB, GPU 메모리)을 쓴다.
- **DWM 프레임**: WGC는 초당 약 60프레임을 받았다. 30fps 녹화에서는 약 절반이 다음 프레임에 밀려 바로 반납됐다.

일시정지 결과는 최신 프레임만 보관하는 설계 때문이다. 녹화기가 프레임을 요청할 때만 `TryGetNextFrame`을 부르는
단순한 방식은 일시정지 중 풀이 가득 차 이후 프레임이 버려지고, 재개 직후 일시정지 시작 무렵의 오래된 프레임을
돌려준다. 그러면 일시정지 동안 화면에 있던 내용이 클립에 들어갈 수 있다.

## 별도 발견: 30fps 페이싱

기존 `--selftest-recording-performance`(정지 화면, WPF 렌더 루프 없음)에서는 두 백엔드 모두 30fps 목표에 약
6초 동안 131~136프레임(21.7~22.5fps)만 기록했다. WGC 캡처 합계는 48~76ms(프레임당 0.4~0.6ms)이고 인코딩도
프레임당 1ms 안팎이므로 캡처가 원인이 아니다. 녹화 루프는 남은 시간을 `Thread.Sleep`으로 기다리는데, 기본
타이머 해상도(15.6ms)에서는 33.3ms 대기가 약 46.9ms로 늘어난다. v1.8.0 증거 문서의 21.8~22.3fps도 같은 현상으로
보인다.

이를 확인하려고 합성 창의 `CompositionTarget.Rendering` 구독까지 끊은 정지 장면에서 1920x1080을 10초씩
측정했다(`MYCAPTURE_BENCH_MATRIX=0`, 두 번 실행).

| 조건 | GDI 실효 fps / 간격 중앙값 | WGC 실효 fps / 간격 중앙값 |
|---|---:|---:|
| 정지 장면, 렌더 루프 없음, 30fps | 21.4 / 46.8ms (2회 동일) | 21.4~21.5 / 46.7ms |
| 정지 장면, 렌더 루프 없음, 60fps | 47.7 / 17.0ms (p95 31.3ms) | **32.0 / 30.9ms** |
| 정지 장면, 렌더 루프 동작, 30fps | 29.8 / 33.3ms | 29.6 / 33.5ms |

간격 46.8ms와 30.9ms는 15.6ms 타이머 세 칸과 두 칸이다. 60fps에서는 GDI의 14ms 캡처가 대기 위상을 밀어
일부 프레임이 17ms 간격으로 들어가지만, WGC는 캡처가 0ms에 가까워 매번 16ms 대기가 두 칸(31.2ms)으로 늘어난다.
**타이머 해상도가 기본값인 조건에서는 WGC 60fps가 GDI보다 오히려 낮다.**

따라서 WGC만으로는 실제 사용 환경의 30fps가 오르지 않고, 60fps는 나빠질 수 있다. 녹화 루프 대기를 고해상도 대기 타이머
(`CreateWaitableTimerExW`의 `CREATE_WAITABLE_TIMER_HIGH_RESOLUTION`)로 바꾸는 작업을 백엔드와 별개로 진행해야 한다.
위 측정표는 렌더 루프가 도는 움직이는 장면이라 이 제약이 드러나지 않은 조건이다.

## 비용과 위험

1. **여러 모니터 합성**: WGC 모니터 항목은 자기 디스플레이만 본다. 여러 모니터에 걸친 영역은 세션 여러 개,
   서로 다른 주사율·도착 시각 정렬, DPI 경계 합성이 필요하다. 스파이크는 이런 영역을 GDI로 폴백하며, 걸친 영역의
   실제 사용 비율은 원격 측정을 두지 않으므로 알 수 없다. 합성 구현보다 폴백 유지가 비용 대비 낫다.
2. **노란 테두리**: 비패키지 실행에서 `RequestAccessAsync(Borderless)`는 확인 창 없이 `Allowed`를 돌려줬고
   `IsBorderRequired`를 다시 읽으면 `false`였다(모든 측정 실행에서 동일). 테두리 표시 여부는 소프트웨어로 확인하지
   못했다. 기본 테두리 세션과 테두리 없음 세션 모두 GDI로 읽은 모니터 가장자리 노란 픽셀은 0이었고 새 최상위 창도
   생기지 않았다. 시스템 테두리가 캡처에서 제외되는 것으로 보이므로 **눈으로 확인하는 수동 QA가 필요하다.**
   다른 앱이 같은 디스플레이를 `IsBorderRequired = true`로 캡처하면 테두리는 다시 보인다(문서화된 동작).
3. **HDR 톤매핑**: 이 PC에서 HDR이 켜진 출력이 없어 미측정이다. 문서상 HDR 디스플레이에서 B8G8R8A8 풀은 시스템
   변환으로 색이 바래 보일 수 있고, 제대로 하려면 R16G16B16A16Float 풀과 톤매핑 셰이더가 필요하다. 셰이더 경로는
   D3D 파이프라인 구성이 늘어나는 별도 작업이다. GDI도 HDR에서 SDR 변환 결과를 받으므로 현재 품질과의 비교 측정이
   필요하다.
4. **스크린샷 경로 적용 시 세션 시작 지연**: WGC 세션 생성이 36~123ms(프로세스 첫 세션은 장치·WinRT 활성화 포함
   116~123ms), 첫 프레임 도착이 4~9ms 더 걸린다. 미리 데운 GDI 정지 캡처(3440x1440 21~51ms, `ScreenCaptureEngine.Prewarm`
   주석의 실측)보다 느리다. 세션을 상시 유지하면 지연은 사라지지만 GPU 메모리를 계속 쓰고 개인정보 측면에서 상시 화면 캡처 세션을 둔다.
   **정지 스크린샷 경로에는 적용하지 않는다.**
5. **보안 데스크톱·DRM**: UAC 보안 데스크톱, 잠금 화면, DRM 보호 재생은 이 스파이크에서 재현하지 않았다(사용자 개입이
   필요해 미실행). 보호 콘텐츠는 두 백엔드 모두 검게 나오는 것이 플랫폼 동작이다. 보안 데스크톱 전환 시 GDI는
   `BitBlt` 실패로 녹화가 실패할 수 있고, WGC는 프레임이 멈춰 마지막 화면이 반복될 수 있다. 어느 쪽이든 수동 QA로
   확인해야 한다.
6. **Store(MSIX) capability**: 현재 `build/store/AppxManifest.xml`은 `runFullTrust`만 선언한다. 문서상
   `RequestAccessAsync(Borderless)`에는 `graphicsCaptureWithoutBorder`(uap11, 일반 capability, Store 승인 불필요)
   선언이 필요하다. 이 capability 없이 패키지에서 실행하면 테두리가 남을 수 있다. `graphicsCaptureProgrammatic`은
   `WindowId`/`DisplayId`로 항목을 만들 때 요구된다고 문서화되어 있으며, 전체 신뢰 패키지의 `CreateForMonitor`에
   필요한지는 확인하지 못했다. **MSIX 빌드에서 미검증**이다.
7. **폴백 전략**: 위 표의 열기·녹화 중 폴백으로 녹화가 실패하지 않고 GDI로 이어진다. 남은 공백은 장치 제거 직후
   첫 프레임이 GDI 경로 생성 시간만큼 늦어지는 것과, 폴백 사실을 사용자에게 알리지 않는 것이다(로그만 남김).
8. **기타 미검증**: Windows 11 22000 실기기(승격 조건), 4K 디스플레이, 저사양·내장 GPU 전용 PC, 디스플레이와 다른
   GPU에 장치가 생기는 하이브리드 노트북, 가상 디스플레이(IddCx)에서의 WGC, 드라이버 재설치·TDR 복구, 혼합 DPI.

## 권고

**조건부 진행.** 단일 모니터 영역 녹화에서 WGC는 같은 PC, 같은 영역 기준으로 GDI보다 캡처 시간(p50) 14~18배 단축,
60fps 고해상도 드롭률 41~48%에서 1.3~2.4%로 감소(렌더 루프가 도는 조건), DWM CPU 절반, 30fps 프로세스 CPU 소폭
감소를 보였고 제외 창, 일시정지, 10분 장시간 녹화, 기존 녹화 self-test를 그대로 통과했다. 그러나 기본 타이머
해상도 조건에서는 녹화 루프 페이싱이 두 백엔드 모두를 30fps 목표 21.4fps로 묶고, 60fps에서는 WGC가 GDI보다
낮다. 또한 P0 승격 조건 중 Windows 11 22000 실기기, 4K, 복구(장치 제거) 실측은 아직 없다.

다음 순서를 권고한다.

1. 녹화 루프 페이싱을 고해상도 대기 타이머로 바꾼다. 백엔드와 무관하게 실제 30fps에 직접 영향을 주고,
   WGC 60fps 이점의 전제 조건이다(이 수정 없이 WGC를 기본값으로 바꾸지 않는다).
2. WGC를 이 스파이크 구조(내부 스위치, GDI 폴백, `Open` 병렬 생성, 최신 프레임 보관)로 정식 브랜치에 옮기되 기본값은
   GDI로 둔다.
3. Windows 11 22000 실기기, 4K, HDR 켜진 디스플레이, 하이브리드 GPU 노트북, MSIX(`graphicsCaptureWithoutBorder` 추가)
   에서 이 self-test와 노란 테두리 육안 확인을 통과하면 단일 모니터 영역의 기본값을 WGC로 바꾼다.
4. 여러 모니터 영역과 정지 스크린샷은 GDI를 유지한다.

중단 조건: 22000 실기기나 MSIX에서 테두리를 끌 수 없거나, HDR에서 GDI보다 품질이 나쁘고 셰이더 비용이 크거나,
보안 데스크톱·장치 제거에서 GDI보다 나쁜 실패가 확인되면 WGC 기본값 전환을 중단하고 60fps 고해상도 전용 선택지로만
남긴다.

## 재현

```powershell
# 백엔드 비교(약 5분, 화면 전체를 합성 창이 덮는다)
$env:MYCAPTURE_BENCH_SECONDS = '10'; $env:MYCAPTURE_BENCH_REPEATS = '2'
MyCapture.exe --selftest-recording-backends <절대 경로>

# 장시간 녹화(백엔드는 MYCAPTURE_RECORDING_BACKEND, 기본 600초 1920x1080 30fps)
$env:MYCAPTURE_RECORDING_BACKEND = 'wgc'; $env:MYCAPTURE_SOAK_SECONDS = '600'
MyCapture.exe --selftest-recording-soak <절대 경로>

# 기존 self-test를 WGC로
$env:MYCAPTURE_RECORDING_BACKEND = 'wgc'
MyCapture.exe --selftest-recording <절대 경로>
MyCapture.exe --selftest-recording-performance <절대 경로>
```

결과는 `recording-backends.json`, `recording-soak.json`, `soak-progress.jsonl`에 원시 값으로 남는다. 성능 수치는
보고만 하고 단언하지 않으며, 판정은 기능 검사(디코드, 제외, 일시정지, 폴백 없음)로만 한다.
