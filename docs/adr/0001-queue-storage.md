# ADR 0001 — 캡처 큐 저장 방식

- 상태: 채택
- 일자: 2026-08-29

## 배경

캡처 큐는 최대 300장(설정 변경 가능)을 보관하고 재시작 후에도 유지되어야 한다.
항목마다 다음을 저장한다.

- 원본 PNG
- 주석 합성 PNG (편집된 경우)
- 주석 레이어 JSON (재편집용)
- 썸네일 PNG (갤러리 격자용)
- 메타데이터: 생성 시각, 크기, DPI 배율, 고정 여부, 바이트 수, OCR 캐시

필요한 질의는 세 가지뿐이다.

1. 생성 시각 역순 정렬 (갤러리)
2. 총 바이트 합계 (용량 상한)
3. 고정되지 않은 가장 오래된 항목 (FIFO 축출)

## 검토안

### 안 A — SQLite (`Microsoft.Data.Sqlite`)

기각.

- 사용 가능한 버전이 `SQLitePCLRaw.lib.e_sqlite3`를 끌어오고, 해당 패키지에
  고위험 권고 GHSA-2m69-gcr7-jv3q가 존재한다. `TreatWarningsAsErrors`에서
  NuGet 감사가 빌드를 중단시켰다.
- 아키텍처별 네이티브 바이너리가 설치 파일에 추가된다.
- 위 세 가지 질의에 SQL 엔진이 필요하지 않다.
- 스키마 마이그레이션이라는 영구 유지보수 부담이 생긴다.

### 안 B — JSON 인덱스 + 원자적 교체

채택.

- 인덱스 파일 하나(`index.json`)에 전체 메타데이터를 담고, 이미지 바이트는
  디스크의 개별 파일로 둔다.
- 시작 시 전량 메모리로 읽는다. 300개는 수백 KB 수준이며 파싱은 밀리초 단위다.
  상한을 5000까지 올려도 문제되지 않는다.
- 쓰기는 임시 파일에 기록한 뒤 `File.Replace`로 교체한다. 부분 기록된 인덱스가
  남지 않는다.
- `File.Replace`가 이전 내용을 백업 파일로 남기므로, 시작 시 인덱스가 손상되어
  있으면 백업에서 복구를 시도할 수 있다.
- 외부 의존성 0, 네이티브 바이너리 0, 마이그레이션 없음.

### 안 C — 항목별 사이드카 JSON

기각. 300번의 파일 열기가 시작 시간을 늘리고, 총 바이트 합계를 구하려면 전량
순회가 필요해 안 B의 이점이 사라진다. 다만 개별 항목 손상이 전체를 망가뜨리지
않는 장점은 있어, 안 B에서 인덱스 손상 시 폴백 경로로 부분 채택한다.
즉 각 캡처 폴더에 최소 메타(`meta.json`)를 함께 남겨 인덱스를 재구성할 수 있게
한다.

## 결론

메모리 인덱스를 단일 `index.json`에 원자적으로 유지하고, 항목별 `meta.json`을
복구용으로 병행 기록한다.

## 되돌릴 조건

다음 중 하나가 발생하면 재검토한다.

- 상한이 수만 장 규모로 올라간다.
- 전문 검색(OCR 텍스트 전문 검색 등)이 필요해진다.
- 인덱스 쓰기가 체감 지연을 유발한다.
