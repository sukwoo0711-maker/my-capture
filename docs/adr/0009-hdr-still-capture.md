# ADR 0009 — HDR 화면 정지 캡처 색 보정

상태: 구현 — HDR을 켠 디스플레이의 실기 확인 대기
기준: MyCapture 5.3.0, `main@dfc497d4`
관련: [ADR 0002](0002-region-recording.md), [ADR 0005](0005-wgc-recording-spike.md), [ADR 0007](0007-windows10-22h2-support.md)

## 배경

HDR을 켠 모니터에서 찍은 정지 캡처가 실제 화면보다 밝고 바랜 색으로 저장됩니다. 정지 캡처는 데스크톱 DC를
GDI `BitBlt`로 복사하며 색을 보정하는 단계가 없었습니다.

HDR이 켜지면 Windows는 데스크톱을 scRGB(선형, BT.709 원색, 1.0 = 80니트, 16비트 부동소수)로 합성합니다. SDR 콘텐츠는
sRGB 전달 함수로 풀어 디스플레이의 **SDR 흰색 수준**(설정의 "SDR 콘텐츠 밝기")만큼 곱하므로 SDR 흰색은
`흰색 수준 / 80`에 놓입니다. GDI가 돌려받는 8비트 사본은 이 배율로 나누지 않은 값을 1.0에서 자른 것으로 설명되며,
그렇다면 중간 톤은 밝아지고 80니트를 넘는 값은 모두 사라져 8비트 사본에서는 원래 값을 복원할 수 없습니다.
이 설명은 scRGB 합성과 SDR 흰색 수준의 문서화된 정의, 그리고 같은 방식으로 보정하는 다른 캡처 도구의 구현과
일치합니다. **이 PC에는 HDR을 켠 디스플레이가 없어 GDI 사본의 실제 값은 확인하지 못했습니다.** 아래 구현은 GDI가
무엇을 돌려주는지에 의존하지 않고, HDR 모니터를 부동소수로 다시 읽어 직접 변환합니다.

## 결정

| 항목 | 결정 |
|---|---|
| 대상 | `ScreenCaptureEngine.CaptureRegion`을 쓰는 모든 정지 캡처(영역·전체 화면·창·지연·스크롤 캡처, 선택 화면이 멈춰 보여 주는 화면, 캡처 준비). 녹화는 대상이 아닙니다. |
| 감지 | 캡처마다 `QueryDisplayConfig`와 `DisplayConfigGetDeviceInfo`로 소스별 고급 색 상태와 SDR 흰색 수준을 읽습니다(`HdrDisplayDetector`). user32만 호출하며 저장해 두지 않습니다. Windows 11 24H2부터는 활성 색 모드가 HDR인 소스만, 그 이전에는 고급 색을 쓰는 소스를 후보로 보고 DXGI 출력의 색 공간(`DXGI_COLOR_SPACE_RGB_FULL_G2084_NONE_P2020`)으로 확정합니다. 광색역 SDR(자동 색 관리)은 HDR이 아니므로 GDI 사본을 그대로 씁니다. |
| 읽기 | DXGI Desktop Duplication의 `IDXGIOutput5::DuplicateOutput1`에 `R16G16B16A16_FLOAT`를 요청해 HDR 모니터의 합성 결과(scRGB)를 한 프레임 읽습니다(`HdrDesktopReader`). 복제 세션은 캡처마다 만들고 바로 닫습니다. |
| 변환 | 흰색 배율로 나눈 뒤 sRGB 전달 함수로 8비트 BGRA를 만듭니다(`HdrToneMap`, 하드웨어와 무관한 순수 코드). SDR 흰색 이하인 픽셀은 반올림까지 정확한 sRGB 값입니다. |
| SDR 흰색보다 밝은 픽셀 | 픽셀 전체를 가장 큰 채널로 나누어 그 채널을 SDR 흰색에 맞춥니다. 채널별로 자르지 않으므로 색조가 바뀌지 않습니다. 음수 채널(sRGB 밖의 색)과 NaN은 0으로, 알파는 불투명으로 씁니다. |
| 합치는 방법 | 지금까지처럼 GDI로 전체 영역을 복사한 뒤, HDR 모니터에 걸친 부분만 변환한 픽셀로 덮어씁니다. HDR이 아닌 모니터의 픽셀은 기존과 한 비트도 다르지 않으며, HDR 모니터와 SDR 모니터에 걸친 영역은 모니터별로 처리됩니다. 커서는 덮어쓴 뒤 기존 방식으로 그립니다. |
| 실패와 지연 | 캡처는 scRGB 읽기를 최대 300 ms 기다립니다. D3D 장치를 새로 만들어야 하는 읽기(앱 시작 때의 준비, 10분 넘게 쉰 뒤의 첫 캡처)만 1,000 ms까지 기다립니다. 실패하거나 늦으면 그 캡처는 GDI 사본을 그대로 쓰고 첫 번째만 경고 로그를 남깁니다. 캡처가 HDR 경로 때문에 실패하지는 않습니다. |
| 설정 | 없습니다. 바랜 색을 원하는 경우가 없고, 실패하면 자동으로 기존 결과가 됩니다. 진단용 환경 변수 `MYCAPTURE_HDR_CAPTURE`만 둡니다(`off`: 보정하지 않음, `force`: HDR이 아닌 모니터도 scRGB로 읽음). |
| 진단 | `MyCapture.exe --selftest-hdr-capture <폴더>` |

## 읽기 방식 선택

Desktop Duplication과 Windows.Graphics.Capture(WGC)의 부동소수 프레임 풀을 같은 PC에서 비교했습니다.
측정은 임시 프로브(`C:\t\hdr\probe`, 저장소 밖)로 했고 HDR이 꺼진 화면을 부동소수로 강제로 읽었습니다.

| 기준 | Desktop Duplication | WGC |
|---|---|---|
| 캡처 테두리 | 없음 | Windows 10에서는 노란 테두리가 보이고, Store 패키지는 테두리 없는 캡처에 동의 창이 뜰 수 있음(ADR 0006) |
| 정지 화면의 첫 프레임 | 새 복제 세션의 첫 `AcquireNextFrame`이 2~10 ms 안에 합성된 화면을 돌려줌(34회 중 34회, 다시 호출하거나 시간 초과한 경우 없음) | `StartCapture` 뒤 3.5~9 ms, 프로세스의 첫 세션은 77 ms. 비동기 이벤트를 기다려야 함 |
| GDI 화면과의 일치(SDR 화면, 3440×1440) | 채널 값 1,486만 개 중 16~148개가 1 차이, 나머지는 같음 | 173만 개가 다르고 최대 87 차이(작업 표시줄 영역 전체) |
| 세션 준비 | `DuplicateOutput1` 0.3~0.9 ms | 세션 생성 13~75 ms |
| 필요한 것 | D3D11 장치(출력이 붙은 어댑터) | D3D11 장치, WinRT 프레임 풀, MTA |
| 회전한 모니터 | 표면이 회전되지 않은 채 오므로 직접 돌려 읽어야 함 | 데스크톱 방향으로 옴 |
| 커서 | 프레임에 없음(기존과 같이 직접 그림) | 세션 속성으로 끔 |
| 캡처에서 제외한 창 | DWM이 제외(GDI와 같음) | DWM이 제외 |

WGC의 부동소수 프레임은 작업 표시줄의 반투명 영역을 다시 합성한 결과여서 SDR 화면에서도 GDI 화면과 달랐습니다.
Desktop Duplication은 테두리와 동의 창이 없고 동기 호출 한 번으로 현재 화면을 얻으므로 이쪽을 택했습니다.
회전은 변환 단계에서 처리하며(`HdrSurfaceGeometry`), 이 PC의 270° 회전 모니터에서 GDI 화면과 비교해 확인했습니다.

## 장치 유지

D3D11 장치를 만드는 데 이 PC(NVIDIA)에서 65~144 ms가 걸렸고, 장치가 있으면 보정 전체가 3440×1440에서 7~10 ms입니다.
캡처마다 장치를 만들면 "두 번째 캡처부터 100 ms 이내"를 지킬 수 없어 장치를 프로세스 안에 두되 다음과 같이 제한합니다.

- 마지막 HDR 캡처 뒤 10분 동안 쓰지 않으면 장치를 해제합니다. 장치가 있는 동안 전용 메모리는 31~32 MB, 스레드는 약 20개 늘어납니다.
- 스테이징 텍스처는 캡처마다 만들고 해제하지만 드라이버가 그 메모리를 풀에 남겨 둡니다(3840×2160 읽기 한 번에 66 MB,
  `Release`와 `Flush` 뒤에도 그대로). 읽기마다 `Flush`해 다음 읽기가 그 메모리를 다시 쓰게 하고, 마지막 읽기 0.5초 뒤
  `IDXGIDevice3::Trim`으로 돌려줍니다(측정: 66 MB → 0~4 MB, 4 ms). 변환한 픽셀을 담는 버퍼도 하나를 남겨 다음 캡처가
  다시 쓰고 같은 때에 해제합니다. 스크롤 캡처처럼 연달아 찍을 때 프레임마다 새 메모리를 받지 않게 하기 위해서입니다.
- 복제 세션은 캡처마다 만들고 닫으므로 잠금·모드 변경·정지 화면에서 세션을 되살리는 처리가 필요 없습니다.
- 유지하던 장치로 실패하면(드라이버 재시작, 어댑터 변경) 장치를 버리고 그 캡처 안에서 새 장치로 한 번 더 시도합니다.
- 읽기는 한 번에 하나만, 별도 스레드에서 실행합니다. 캡처가 한도 안에 결과를 받지 못하면 기다리기를 그만두고,
  그 읽기가 끝날 때까지 다음 캡처들은 기다리지 않고 바로 GDI 사본을 씁니다. 늦게 끝난 읽기의 단계별 시간은
  다음 HDR 캡처 때 로그에 남습니다.
- 한도는 장치가 있을 때 300 ms, 장치를 만들어야 할 때 1,000 ms입니다. 장치 생성은 평소 72~144 ms였지만 다른 작업이
  CPU를 쓰는 동안에는 172~326 ms였고, 그때 첫 읽기 전체는 211~497 ms였습니다. 300 ms에서 포기하면 HDR 화면에서
  바랜 사본이 저장되므로 이 한 번의 읽기에만 더 긴 한도를 줍니다.
- 유지하는 장치는 하나입니다. HDR 모니터가 서로 다른 그래픽 어댑터에 붙어 있으면 어댑터가 바뀔 때마다 장치를 다시
  만듭니다(한계 참조).
- 앱 시작 때의 캡처 준비(`ScreenCaptureEngine.Prewarm`)가 HDR 모니터마다 1픽셀을 읽어 장치와 변환 표를 미리 만듭니다.
  HDR 모니터가 없으면 디스플레이 구성 조회 한 번만 더 합니다.

## 측정

PC: AMD Ryzen 7 9800X3D(16스레드), NVIDIA GeForce RTX 5080, Windows 11 Home 10.0.26200.
디스플레이: DISPLAY1 3440×1440, DISPLAY2 768×1366(가상 디스플레이, 270° 회전). 둘 다 HDR 꺼짐(지원은 함), SDR 흰색 80니트.
3840×2160 디스플레이가 없어 읽기 시간은 3440×1440에서 쟀고 변환만 3840×2160 크기로 따로 쟀습니다.

아래 값은 `--selftest-hdr-capture`를 프로세스를 새로 띄워 다섯 번 실행한 결과입니다(HDR이 꺼진 화면을 scRGB로
강제로 읽음). 같은 PC에서 다른 작업이 CPU를 쓰는 동안 잰 값은 따로 적었습니다.

| 항목 | 값 |
|---|---|
| 감지 1회(디스플레이 2개) | 중앙값 0.011~0.016 ms, p95 0.013~0.022 ms(n=1,000). 프로세스의 첫 호출은 1.2~2.0 ms |
| HDR이 없을 때 캡처에 더해지는 시간 | 1픽셀 캡처 중앙값 8.31~8.34 ms(보정 끔) 대 8.35~8.38 ms(자동), 차이 0.02~0.06 ms(각 200회, 번갈아 측정). 앞선 빌드의 실행까지 합치면 −0.04~+0.07 ms |
| 3440×1440 첫 캡처(장치 생성 포함) | 읽기 131~138 ms: 장치 생성 110~116 ms, 변환 표 준비와 변환 10.3~10.9 ms, 프레임 대기 2.2~2.6 ms, 복사 3.3~3.5 ms. 빌드한 뒤 처음 띄운 실행은 181 ms(장치 생성 144 ms) |
| 3440×1440 이후 캡처(장치 유지) | 보정에 7.3~9.8 ms: 출력 찾기 0.4, 복제 세션 0.3, 프레임 대기 2.3~5.0, GPU 복사와 매핑 1.0~1.1, 변환 1.5~1.7, 덮어쓰기 약 1 ms. 25회 중 2회는 프레임 대기가 7~9 ms여서 12~14 ms. 같은 화면의 GDI 캡처는 20~29 ms |
| 768×1366(270° 회전) 이후 캡처 | 보정에 7.6~9.2 ms(60 Hz 화면이라 프레임 대기가 대개 5.5~6.8 ms) |
| 쉰 뒤 장치를 다시 만드는 캡처 | 읽기 78~89 ms(장치 생성 72~84 ms) |
| 다른 작업이 CPU를 쓰는 동안 | 첫 읽기 211~278 ms(장치 생성 172~202 ms), 이후 캡처 보정 7~80 ms, 한 번은 112 ms. 런타임 설정을 바꿔 본 실행 하나는 첫 읽기 497 ms(장치 생성 326 ms). 테스트 프로세스에서 첫 읽기가 한 번 300 ms를 넘김 |
| 3840×2160 변환만 | SDR 그림: 한 스레드 9.4~9.9 ms, 16개 띠로 나누어 1.6~2.2 ms. 픽셀의 34 %가 SDR 흰색보다 밝은 그림: 한 스레드 26.7~28.2 ms, 16개 띠 4.5~5.0 ms(합성 그림, 9회 중앙값) |
| 메모리 | 장치를 유지하는 동안 전용 메모리 31~32 MB, 해제하면 돌아옴 |

3840×2160 모니터에서의 읽기 시간은 재지 못했습니다. 3440×1440 값에서 화소 수에 비례하는 단계(복사, 변환, 덮어쓰기)를
1.67배 하면 이후 캡처의 보정은 10~12 ms, 첫 캡처의 읽기는 135~145 ms로 예상됩니다. 목표(첫 캡처 300 ms, 이후 100 ms 이내)
안쪽이지만 실제 4K HDR 모니터에서 확인해야 합니다. 다른 작업이 CPU를 많이 쓰는 동안에는 이후 캡처 한 번이
112 ms로 100 ms를 넘었습니다.

픽셀마다 도는 변환 메서드는 `MethodImplOptions.AggressiveOptimization`으로 처음부터 완전 최적화 코드로 컴파일합니다.
런타임의 계층 컴파일에 맡겼을 때는 계측 단계(동적 PGO)를 지나는 동안 한 세션의 캡처 한두 번에서 3440×1440 변환이
약 3 ms에서 19~24 ms로 느려졌습니다(기본 설정 7회 실행 모두, `DOTNET_TieredPGO=0`으로 실행한 2회에서는 없음).
계측용 코드가 느린 데다 그 카운터를 변환 스레드 16개가 함께 쓰기 때문으로 봅니다(띠마다 고르게 약 8배 느려짐).
바꾼 뒤 방해받지 않은 다섯 번의 실행에서는 이후 캡처 25회의 변환이 모두 1.5~1.7 ms였습니다. 대신 프로필 기반
최적화가 빠져 SDR 흰색보다 밝은 픽셀이 많은 그림의 변환은 3840×2160에서 16개 띠 기준 2.5~2.8 ms에서
4.5~5.0 ms로 늘었습니다.

self-test는 같은 화면을 GDI로 한 번, 보정 경로로 한 번, 다시 GDI로 한 번 찍어 두 GDI 그림에서 값이 같은 픽셀만
비교하고, 화면마다 채널 값의 99.9 % 이상이 1 이내일 때 통과로 판정합니다. 두 GDI 캡처 사이에 바뀌었다가 돌아온
픽셀은 걸러지지 않으므로 위 표의 "차이 2 이상"처럼 남을 수 있고, 보고서에 그 범위가 좌표로 적힙니다.
테스트의 고정 무늬 창(320×240)은 한 모니터 안에서도, 두 모니터에 걸쳐서도 모든 픽셀이 1 이내였고, 캡처에서
제외한 창(`WDA_EXCLUDEFROMCAPTURE`)은 scRGB 읽기에서도 보이지 않았습니다.

## 한계

- HDR을 켠 디스플레이에서 본 결과가 없습니다. 감지, 흰색 수준, HDR 색 공간 확인, 실제 scRGB 값의 변환은
  아래 실기 확인으로만 검증됩니다.
- 회전은 270°만 실제 모니터로 확인했습니다. 90°와 180°는 같은 변환식의 단위 테스트로만 확인했습니다.
- DIB 섹션을 만들지 못해 호환 비트맵으로 읽는 예비 경로(`CaptureRegionCore`)에는 보정을 넣지 않았습니다.
- SDR 화면을 부동소수로 읽으면 작업 표시줄 아이콘의 반투명 가장자리 수십 픽셀이 GDI 화면과 다릅니다(회전 모니터에서
  78픽셀, 최대 23). 변환 오차가 아니라 DWM이 부동소수 표면에 합성한 결과의 차이이며, HDR 화면에서는 그 표면이
  실제로 표시되는 화면입니다.
- 야간 모드, 색 필터처럼 합성 뒤에 적용되는 효과가 scRGB 표면에 들어 있는지는 확인하지 못했습니다.
- 하이브리드 GPU 노트북, 내장 GPU, Windows 10 22H2에서는 실행해 보지 않았습니다. 읽기에 실패하면 GDI 사본을 씁니다.
- 유지하는 D3D 장치가 하나여서, HDR 모니터가 서로 다른 그래픽 어댑터에 붙어 있으면 모니터를 바꿔 찍을 때마다
  장치를 다시 만듭니다(이 PC에서 72~144 ms). 그런 두 모니터에 걸친 영역은 한 캡처에 장치를 두 번 만들므로 300 ms
  한도를 넘겨 GDI 사본이 될 수 있습니다. 그런 구성이 없어 실행해 보지 않았습니다.
- x86 빌드, 배포용(ReadyToRun) 빌드, Store 패키지에서는 실행해 보지 않았습니다.

## 톤 연산자

기본 연산자는 SDR 값을 그대로 보존하는 대신 SDR 흰색보다 밝은 부분의 계조를 잃습니다(모두 그 색조의 가장 밝은 SDR 색이 됩니다).
비교용으로 soft knee 연산자를 코드에 남겼습니다. SDR 흰색의 75 %부터 디스플레이 최대 밝기까지를 75~100 %로 눌러
담으므로 밝은 부분의 계조가 남지만, 밝은 SDR 값이 어두워집니다(SDR 흰색 255가 SDR 흰색 200니트·최대 1,000니트 기준 241).
제품 캡처는 기본 연산자만 쓰고 soft knee는 self-test의 비교 그림에만 쓰입니다. 화면도 설정도 없습니다.

## 녹화

녹화 파이프라인은 바꾸지 않았습니다. 녹화에 같은 보정을 넣으려면 다음이 필요합니다.

- WGC 프레임 풀을 `R16G16B16A16Float`로 만들고, 프레임마다 CPU로 읽지 않도록 GPU 셰이더에서 흰색 배율과 톤 연산,
  sRGB 변환(또는 NV12 변환까지)을 수행하는 단계.
- 녹화 중 SDR 흰색 수준이나 HDR 상태가 바뀌는 경우의 처리(프레임 풀 재생성, 배율 갱신).
- 여러 모니터에 걸쳐 GDI로 녹화하는 경로는 프레임마다 Desktop Duplication을 유지해야 하므로 세션 수명 관리
  (잠금, 모드 변경, 정지 화면의 프레임 재사용)가 필요합니다.
- 60 fps에서의 프레임 예산 측정과 HDR 디스플레이 실기 비교(ADR 0005 위험 3, ADR 0006 검증 항목 4).

## HDR을 켠 PC에서 확인할 것

```powershell
$exe = '<폴더>\MyCapture.exe'
$out = Join-Path $env:TEMP ('MyCapture-hdr-' + [guid]::NewGuid().ToString('N'))
Start-Process -Wait -PassThru -FilePath $exe -ArgumentList '--selftest-hdr-capture', $out
Get-Content -LiteralPath (Join-Path $out 'hdr-capture-report.txt')
```

1. Windows 설정에서 HDR을 켜고 "SDR 콘텐츠 밝기"를 가운데쯤에 둡니다. 메모장, 탐색기, 브라우저처럼 색을 아는
   SDR 창과, 가능하면 HDR 동영상이나 HDR 사진을 화면에 둡니다.
2. 위 명령을 실행합니다. 보고서의 해당 모니터 줄이 `HDR active=True`, 표면 형식 `R16G16B16A16_FLOAT`, DXGI 색 공간 12,
   설정한 밝기에 맞는 SDR 흰색(80~480니트), 결과 `Applied`여야 합니다.
3. `<모니터>-gdi.png`(기존 방식)와 `<모니터>-converted.png`(보정)를 비교합니다. 보정한 그림의 SDR 창은 화면에서 보던
   색과 같아야 하고, GDI 그림은 그보다 밝고 바래 있어야 합니다. GDI 그림이 이미 정상이면 배경의 가설이 그 PC에서는
   맞지 않는 것이므로 두 그림을 보관해 알려 주십시오.
4. 같은 SDR 창을 HDR을 끄고 찍은 캡처와 `-converted.png`의 같은 위치 색을 비교합니다(선택 화면의 `C` 키로 색 값을 읽을 수
   있습니다). 채널마다 1 이내로 같아야 합니다.
5. HDR 콘텐츠의 밝은 부분은 `-converted.png`에서 색조가 유지된 채 흰색 수준으로 낮아져 있어야 합니다. 계조가 더 필요하면
   `-converted-soft-knee.png`와 비교하고, 합성 그림 `synthetic-hdr-default.png`·`synthetic-hdr-soft-knee.png`도 참고합니다.
6. 보고서의 첫 캡처와 이후 캡처 시간(`later capture`)이 각각 GDI 단독보다 300 ms, 100 ms 이상 늘지 않았는지 봅니다.
   `WARNING: the first read missed its budget` 줄이 있으면 어느 단계가 느렸는지 함께 적혀 있습니다.
7. 앱에서 영역 캡처, 전체 화면 캡처, 창 캡처를 해 저장된 그림과 선택 화면의 색이 화면과 같은지 봅니다.
   HDR 모니터와 SDR 모니터에 걸친 영역도 한 번 찍어 경계 양쪽이 각각 맞는지 확인합니다.
8. 문제가 있으면 `MYCAPTURE_HDR_CAPTURE=off`로 실행해 기존 결과와 비교하고, 로그의 `HDR display` 줄을 함께 보냅니다.
